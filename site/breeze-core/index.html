Breeze Core

Self-hosted, LAN-first control for Midea air conditioners: a REST API, a web panel, device-pairing authentication, server-side schedules and temperature curves. No cloud account, no vendor app, nothing phoning home.

Add the aspic repository first — one snippet for your system, once — and then this is a single command. There is no separate repository for this project. 
sudo apt install breeze-core        # Debian family
sudo dnf install breeze-core        # Fedora / RHEL family
sudo zypper install breeze-core     # openSUSE
sudo pacman -S breeze-core          # Arch family
sudo apk add breeze-core            # Alpine
opkg install breeze-core            # OpenWrt

After installing

Three steps, and the first one is the only one that needs your air conditioners switched on 
# 1. find the units on your network and write the config
sudo breeze-core pair

# 2. bind somewhere useful: your LAN address for direct use, or leave it on
#    127.0.0.1 with a reverse proxy in front
sudoedit /etc/breeze-core/breeze-core.env

# 3. start it
sudo systemctl enable --now breeze-core

Then open http://<that address>:8420. The panel asks for the API key once per device — it is in /etc/breeze-core/config.json, which pair wrote — and then asks an admin on the local network to approve the pairing:

sudo breeze-core approve --config /etc/breeze-core/config.json <CODE>
sudo breeze-core devices     # what is enrolled
sudo breeze-core diag        # is anything wrong
A V3 unit needs a token and key. Nearly every unit sold now is V3, and Midea will only issue those credentials to the account the unit is registered to — its cloud stopped handing them out to anyone else. pair takes a token and key if you already have them, and there is a last-resort path that asks for your Midea account once and forgets it. Keep a copy of config.json somewhere else: those credentials are not re-issuable.

From the command line

The whole server is one binary, and it is also the client 
breeze-core control 'kuhinja' cool 25.5 both auto turbo 15m
breeze-core control 'lijeva soba' heat 22 horizontal low eco
breeze-core control 'dnevna soba' none none none none none 30m

Name, mode, temperature, flap, fan, extra, timer — in that order, with none valid anywhere and names matched case insensitively (or by any unambiguous prefix). It enrols itself the first time you use it, like any other client.

What you get

one binary~2.5 MB, no interpreter, no runtime, nothing installed alongside it. The web panel is compiled into it
the API30 endpoints, key + per-device-token auth, an SSE stream for live state, Prometheus metrics
schedulesfavourites, weekly schedules and interpolated temperature curves, run server-side — nothing has to stay open
an Android appBreeze, which talks to the same API
architecturesx86-64, arm64, armv7, riscv64, ppc64le, s390x — and routers, which the previous line could not fit on

Coming from 3.x

The Python implementation, still published on bolero

4.0.0 is the same project reimplemented — same REST API, same config.json, devices.json, programs.json and timers.json, same AC_* environment variables, same service name, same web panel and the same Android app. It is meant to be installed over a 3.x deployment rather than migrated to, and the existing paths it does not need any more are kept as symlinks so nothing that names them breaks.

Everything published for 3.x stays exactly where it is on bolero and keeps installing; nothing is being switched off underneath anyone.

Back up /etc/breeze-core before any upgrade. Not because this one is risky — an upgrade keeps the directory — but because a paired V3 unit's credentials cannot be obtained again, and that is true whatever you are upgrading.
