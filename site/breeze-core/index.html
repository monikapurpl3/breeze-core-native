aspic / breeze-core

Breeze Core

Self-hosted, LAN-first control for Midea air conditioners: a REST API, a web panel, device-pairing authentication, server-side schedules and temperature curves. No cloud account, no vendor app, nothing phoning home.

Add the aspic repository first — one snippet for your system, once — and then this is a single command. There is no separate repository for this project. 
sudo apt install breeze-core        # Debian family
sudo dnf install breeze-core        # Fedora / RHEL family
sudo zypper install breeze-core     # openSUSE
sudo pacman -S breeze-core          # Arch family
sudo apk add breeze-core            # Alpine
opkg install breeze-core            # OpenWrt
pkgin -y install breeze-core        # NetBSD
pkg install breeze-core             # FreeBSD

OpenBSD and OPNsense install one named file rather than a package by name — the OpenBSD and OPNsense sections on the index have the command.

After installing

Three steps, and the first one is the only one that needs your air conditioners switched on 
# 1. find the units on your network and write the config
sudo breeze-core pair

# 2. bind somewhere useful: your LAN address for direct use, or leave it on
#    127.0.0.1 with a reverse proxy in front
sudoedit /etc/breeze-core/breeze-core.env

# 3. start it
sudo systemctl enable --now breeze-core

Step 2's file moves with the platform's prefix: /usr/local/etc/breeze-core on FreeBSD and OPNsense, /usr/pkg/etc/breeze-core on NetBSD, %ProgramData%\breeze-core on Windows — or set AC_CONFIG_DIR once and stop thinking about it. Step 3 is whatever your init system is:

systemd

Debian · Ubuntu · Fedora · RHEL · SUSE · Arch · Gentoo (systemd profile) 
sudo systemctl enable --now breeze-core
sudo systemctl status breeze-core
journalctl -u breeze-core -f            # follow the log

OpenRC

Alpine · Artix (openrc) · Gentoo · Devuan 
sudo rc-update add breeze-core default
sudo rc-service breeze-core start
sudo rc-service breeze-core status

On Gentoo the settings live in /etc/conf.d/breeze-core, which is where OpenRC expects them — not in breeze-core.env.

runit

Void · Artix (runit) 
# The Void package already ships /etc/sv/breeze-core, disabled.
# Enabling it is the symlink and nothing else:
sudo ln -s /etc/sv/breeze-core /var/service/
sudo sv status breeze-core

Installed by hand instead? The templates are deploy/init/runit-run and its companion runit-log-run, which gives you a rotated log under /var/log/breeze-core rather than runit's catch-all.

s6 / s6-rc

Artix (s6) · Obarun 
sudo mkdir -p /etc/s6/sv/breeze-core
sudo install -m 0755 deploy/init/s6-run /etc/s6/sv/breeze-core/run
sudo s6-rc-bundle-update add default breeze-core
sudo s6-rc -u change breeze-core

SysV init

Devuan (sysvinit) · Slackware · older LTS releases 
sudo install -m 0755 deploy/init/sysv-breeze-core /etc/init.d/breeze-core
sudo update-rc.d breeze-core defaults   # RHEL-ish: chkconfig --add
sudo service breeze-core start

procd

OpenWrt 
/etc/init.d/breeze-core enable
/etc/init.d/breeze-core start
logread -e breeze-core                  # follow the log

rc.d — FreeBSD and OPNsense

FreeBSD 14 · 15 
sudo sysrc breeze_core_enable=YES
sudo service breeze_core start
sudo service breeze_core status

Underscore, not hyphen: FreeBSD's rc system needs a name that is a valid shell variable. On OPNsense the GUI does this for you — Services > Breeze Core.

rc.d — NetBSD

echo 'breeze_core=YES' | sudo tee -a /etc/rc.conf
sudo service breeze_core start

rcctl — OpenBSD

doas rcctl enable breeze_core
doas rcctl start breeze_core
doas rcctl check breeze_core

OpenBSD has no service(8) at all; rcctl is the whole interface.

launchd

macOS — a LaunchDaemon, not an Agent 
sudo cp deploy/init/com.breeze.core.plist /Library/LaunchDaemons/
sudo chown root:wheel /Library/LaunchDaemons/com.breeze.core.plist
sudo launchctl load /Library/LaunchDaemons/com.breeze.core.plist

A daemon rather than an agent, because an agent only runs while its user is logged in — the wrong lifetime for something a phone talks to. The plist creates no account; the header comments carry the three dscl lines.

supervisord

Anywhere, and the usual answer inside a container that runs more than one thing 
sudo cp deploy/init/supervisor-breeze-core.conf \
  /etc/supervisor/conf.d/breeze-core.conf
sudo supervisorctl reread && sudo supervisorctl update

Windows service

Registered by the installer, supervised by NSSM 
Get-Service BreezeCore
Restart-Service BreezeCore
Get-Content "$env:ProgramData\breeze-core\logs\service.log" -Tail 40 -Wait

Containers

docker compose up -d
docker logs -f breeze-core

Writing your own? Three things matter. Pass serve explicitly — a bare breeze-core prints its usage and exits 0, which as a start command looks like success and leaves you with no server. Run it in the foreground and let your supervisor own it; there is no --daemonize. And stop it with a plain TERM: every store is written to a temporary file and renamed into place, so no signal can catch one half-written.

Then open http://<that address>:8420. The panel asks for the API key once per device — it is in /etc/breeze-core/config.json, which pair wrote — and then asks an admin on the local network to approve the pairing:

sudo breeze-core approve --config /etc/breeze-core/config.json <CODE>
sudo breeze-core devices     # what is enrolled
sudo breeze-core diag        # is anything wrong
A V3 unit needs a token and key. Nearly every unit sold now is V3, and Midea will only issue those credentials to the account the unit is registered to — its cloud stopped handing them out to anyone else. pair takes a token and key if you already have them, and there is a last-resort path that asks for your Midea account once and forgets it. Keep a copy of config.json somewhere else: those credentials are not re-issuable.

From the command line

The whole server is one binary, and it is also the client 
breeze-core control 'kitchen' cool 25.5 both auto turbo 15m
breeze-core control 'living room' heat 22 horizontal low eco
breeze-core control 'back room' none none none none none 30m

Name, mode, temperature, flap, fan, extra, timer — in that order, with none valid anywhere and names matched case insensitively (or by any unambiguous prefix). It enrols itself the first time you use it, like any other client.

On Windows

A guided installer, a service, and an optional reverse proxy — no interpreter to install first

Breeze-Core-Setup-@VER@.exe (1.2 MB · sha256) lays down one executable, registers a hardened service under NSSM as LOCAL SERVICE, locks down %ProgramData%\breeze-core, and opens one firewall rule restricted to your local subnet.

It needs no internet: the whole server is that one file, so there is nothing to download during setup. Public HTTPS is a separate, optional component — a guided Caddy wizard that fetches Caddy, writes a hardened config with automatic certificates and a LAN-only admin gate, and can install a fail2ban-style watcher that bans abusive addresses through Windows Firewall. Your LAN is never banned.

Then: Pair AC units from the Start menu (or breeze-core pair), edit breeze-core.env if you want it on the LAN rather than loopback, and nssm start BreezeCore. Uninstalling keeps your configuration unless you ask it not to.

Migrating from 3.x

One script: it works out your package manager, backs everything up, swaps bolero for aspic and upgrades the package
Do not trust scripts you find on the internet. Not this one either. What you are being offered is a file that runs as root on a machine you care about, from a server you have no particular reason to trust, and the fact that this paragraph exists proves nothing — it was written by the same people who wrote the script.

So read it. It is mostly comments, and the parts that delete things are marked. The checksum tells you the download was not corrupted; it cannot tell you the file is safe, because it comes from the same place. Reading is the only real check you have.
curl -fsSL https://aspic.salataputarica.hr.eu.org/migrate.sh -o migrate.sh
less migrate.sh            # the important step
sudo sh migrate.sh         # prints the plan, changes nothing
sudo sh migrate.sh --yes   # does it

Or, once you have read it: curl -fsSL https://aspic.salataputarica.hr.eu.org/migrate.sh | sudo sh -s -- --yes

Run without --yes it prints what it found and what it would change, and stops. That is the default on purpose.

it detectsyour OS, architecture and package manager — apt, dnf, zypper, pacman, apk, opkg, pkgin, pkg (FreeBSD) or pkg_add (OpenBSD)
it backs up/etc/breeze-core and your repository files and keys, into a timestamped root-only directory, with a generated ROLLBACK.sh holding the exact commands for your machine — not "restore from your backup"
it removesthe bolero repository and its signing key
it addsthe aspic repository and its key
it upgradesbreeze-core 3.x to 4.x. The package name is unchanged, so this is an upgrade in place: your configuration, device tokens, programs and timers are untouched and the service stays enabled
it leaves alonea service that was already stopped, and anything it cannot do safely — a source install is refused rather than half-converted

Verified by installing the real Python 3.2.0 from bolero and migrating it: Debian 12, AlmaLinux 9, Arch and Alpine 3.20 in clean containers, and NetBSD 11 and FreeBSD 15.1 on real machines — on FreeBSD that means 3.2.0 with its python312 dependency replaced by a 2.4 MB executable with none, config and device tokens untouched.

OpenBSD is the one case it refuses. The Python line only ever installed from source there, so pkg_add owns none of it and cannot replace it — and removing a service and a virtualenv is not something this script will do behind your back. It stops and prints the three commands to do it yourself, keeping your configuration; run it again afterwards and it installs the native package. Both halves of that were walked on OpenBSD 7.9.

Coming from 3.x

The Python implementation, still published on bolero

@VER@ is the same project reimplemented — same REST API, same config.json, devices.json, programs.json and timers.json, same AC_* environment variables, same service name, same web panel and the same Android app. It is meant to be installed over a 3.x deployment rather than migrated to, and the existing paths it does not need any more are kept as symlinks so nothing that names them breaks.

Everything published for 3.x stays exactly where it is on bolero and keeps installing; nothing is being switched off underneath anyone.

Back up /etc/breeze-core before any upgrade. Not because this one is risky — an upgrade keeps the directory — but because a paired V3 unit's credentials cannot be obtained again, and that is true whatever you are upgrading.
